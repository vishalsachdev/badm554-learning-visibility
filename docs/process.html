The mental model

One orchestrator, many agents, context in files

My context lives on my own filesystem, in plain files and git repositories. Any agent can pick it up and work on it. One orchestrator in the terminal sends each job to the agent that fits it.

This page used four AI tools from three companies (OpenAI, Anthropic and Google), plus media tools that run on the laptop. A desktop app is usually locked into one ecosystem, so it can call only its own models and its own connectors. The command line has no such lock. If a tool has a command-line interface, the orchestrator can run it, read the result from a file and pass it on.

What the command line allows

  • Mix models and companies in one task.
  • Send student data to the one tool approved for it, and keep it away from the rest.
  • Keep a record of every call, because each step is a command and a file.
  • Change the agent later without moving the context.

What a single desktop app usually allows

  • Its own models and its own connectors.
  • Context stored inside the app, in its own format.
  • Handoffs by copy and paste.
  • Rules about data enforced by the vendor, not by you.

Who did what

Chat sessions

The draft came from a conversation. I talked the report through with ChatGPT in voice mode. That assistant (I call it Jev) wrote the draft and the learning-team add-on, then committed both to the program repository as handoff notes for a coding agent to pick up. A conversation is a fast way to get the argument down. It is not a way to check it.

The review was a separate session. A Claude Code session, running in the terminal inside the program repository, picked up the handoff. It read the program's design documents, the Canvas help pages and the Canvas MCP README against the draft's claims. It recounted the issue and pull request counts. It handed every claim about student work to Codex Edu (see below) and published a private reader version. I asked for a page to share with people; it built this site from the reviewed text.

Each repository has its own session. I run these agents in Herdr, a terminal workspace manager for coding agents. Each repository gets one workspace and one long-running session: one for the program, one for each course section, one for this site. When one session needs work done in another repository, it writes a short handoff note into that repository's inbox folder instead of editing files it does not own. The cleanup request for the course repository went that way. The session that owns the repository decides when to act on it.

The evidence base

Real course records

The findings rest on records the course already keeps, not on data collected for this page. BADM 554 runs its operations in a GitHub repository. When the instructor and the AI tools check student work, send messages or enter grades, the work is planned in an issue, and the result is posted back to the issue as a receipt: what was checked, what was sent, what was confirmed in Canvas, and what failed.

The review screened all 51 issues and 27 pull requests in the course repository and read the full discussion on 12 issues. It also looked at 33 issues in the SQL tutor project and 25 in the course textbook. The four cases on the findings page come from those receipts. They are described in words, with class-level counts only, and the smallest counts are softened so that no student can be picked out.

The records were not re-tested live. A receipt says what the tool reported at the time. It is good evidence that a step happened, and weaker evidence that it worked as intended.

Student data

Privacy protection with Codex Edu

My rule is that student data (submissions, rosters, grades, issue comments that mention students) goes only to Codex signed in to the university's ChatGPT Edu account. Other AI tools get de-identified output, aggregates or a file path.

  1. Claude wrote the questions, not the answers

    The review session drew 11 checkable claims from the draft. It wrote a prompt that asked Codex to judge each claim against its source and to report any student identifiers it found, without quoting them.

  2. Codex Edu read the sources

    Codex ran in a read-only sandbox on copies of six course issues, two SQL tutor issues, two audit notes and the dashboard plan.

  3. Claude saw verdicts only

    The result: 10 claims supported and 1 partly supported, because one warning came from a different audit note than the draft said. Claude never read the raw sources.

  4. The raw copies were deleted

    After the check, the copies were removed. The prompt and the de-identified verdicts are kept with this site's working files.

  5. The check found identifiers to clean up

    Two sources held student identifiers: one GitHub username in an issue thread, and student first names in a planning document. Neither reached this page. A cleanup request for the planning document went to the course repository.

The gap, stated honestly: the first draft was written on a ChatGPT Pro account, not the Edu account, and that conversation had read some of the same sources. The Codex Edu check closed the gap for the review. It did not close it for the draft.

The audio transcript was also scanned for names and issue numbers before publication. It holds none, apart from the author's name.

How the agents reach things

Command-line access to everything

An agent can only check what it can reach. Every system in this project has a command-line or protocol interface, so one terminal session could read the course repository, query Canvas, hand student data to Codex Edu, drive NotebookLM and process the audio, all with a record of each call.

The commands, in order

A shortened record of what the orchestrator ran for this page. File names are simplified, and the course repository's name is left out.

# 1. read the course records
gh issue list --repo <course-repo> --state all --limit 200
gh pr list --repo <course-repo> --state all

# 2. hand the student-record claims to Codex on the Edu account
codex exec --sandbox read-only -o VERDICT.md "$(cat PROMPT.md)"

# 3. make the audio overview
notebooklm create "Learning Visibility in BADM 554"
notebooklm source add --type file report.md
notebooklm generate audio --format deep-dive --wait "<prompt>"
notebooklm download audio overview.m4a

# 4. encode and transcribe on the laptop
ffmpeg -i overview.m4a -ac 1 -b:a 80k learning-visibility-audio.mp3
whisper-cli -m ggml-base.en.bin -otxt -ovtt -f audio.wav

# 5. check the prose, then publish
python3 outbound_check.py docs/index.html
git commit && git push
gh repo edit --visibility public
gh api -X POST repos/<owner>/<repo>/pages -f "source[path]=/docs"

The audio overview

Connecting to NotebookLM

NotebookLM has no official public API for personal accounts. The open-source notebooklm-py project drives it through the same web endpoints the browser uses. It is unofficial, so it can break when Google changes the site. The steps were:

# install the command-line tool
uv tool install "notebooklm-py[browser]"

# sign in once, in a real Chrome window
notebooklm login --browser chrome

# make a notebook and add the reviewed report as its only source
notebooklm create "Learning Visibility in BADM 554"
notebooklm source add --type file learning-visibility-badm554.md

# generate a two-host deep-dive audio overview and wait for it
notebooklm generate audio --format deep-dive --length default --wait "<prompt below>"

# download it
notebooklm download audio learning-visibility-badm554.m4a

The prompt named the audience and the limits: "Audience: Gies College of Business faculty and the learning team. Explain how BADM 554 makes student reasoning visible with GitHub, AI-assisted review and Canvas. Keep what the course records show separate from what they do not show yet: do not claim learning gains or faculty time savings. Use the four course cases as concrete examples. Treat the learning-team section as a separate, optional proposal, not part of the main findings."

One sign-in bug. On version 0.8.4, notebooklm login printed "Already logged in" on a signed-out page and saved a session without the sign-in cookies, so every later command failed. The project had already fixed this in its issue tracker. Upgrading to 0.8.5 and signing in again with --fresh solved it. The lesson: check that a sign-in works with a test call before trusting the message that says it did.

After the download, ffmpeg re-encoded the audio to mono MP3, and whisper-cli with the base English model made the transcript and the caption file. One recognition error, the author's surname, was corrected by hand.

Editorial choices

What was not used, and why

NotebookLM made three more items from the same source. Only one made it onto the page, and only after it was redrawn.

  • The mind map: used, redrawn. Its five branches became the Git diagram on the findings page, rebuilt as text so a screen reader can follow it.
  • The infographic: not used. It said Canvas gives "unconfirmed delivery of grades and messages", which is wrong. It credited the tools with capturing reasoning, framed Canvas as shallow, and its text was part of an image, so a screen reader could not read it.
  • The interactive learning overview: not used. It had five factual errors or added details. It placed the discussion review in the wrong module, invented penalties and causes that the records do not state, said grades were final when they had not been posted, and called a checked audit "automated". It also aimed its learning objectives at students rather than at the faculty audience.

The audio overview has the same risk. It is a lively retelling, and it makes some points more strongly than the report does. That is why the page says the report holds where the two differ.
